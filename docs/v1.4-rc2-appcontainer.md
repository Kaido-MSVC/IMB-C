# IMB-C 1.4.0-rc.2 — P1 修正：每工作 AppContainer 隔離

日期：2026-11-18。範圍：RC1 審查 H-1（FAT／exFAT 來源保護）、H-2（磁碟硬配額）、H-3（Low IL 工作隔離）。本文件記錄設計、實測證據與仍未解決的部分；凡是模擬或未執行的項目都另外標明。

> 第二輪（Codex 獨立複查 H2／H3／M1／M2）已取代本文件的 runtime ACL 做法（第 2 節 `ensure_runtime_access`、第 7 節第 3 點）與輸出驗證控制代碼的描述，見 [v1.4-rc2-round2.md](v1.4-rc2-round2.md)。

## 1. 為什麼改用 AppContainer

三項 P1 的共同根因是：引擎程序只有 Low IL。Low IL 只阻擋「寫入完整性較高的物件」，因此：

- 可以讀取大多數使用者檔案、可以連網；
- 可以寫入同使用者所有 Low 標籤物件（其他轉檔工作的暫存、`%USERPROFILE%\AppData\LocalLow`）；
- 在沒有安全描述元的 FAT／exFAT 上完全不受限制；
- 因此可寫位置分散，無法用單一目錄的監控涵蓋（H-2）。

AppContainer 是 Windows 8 起正式支援的隔離機制。AppContainer Token 的每次存取檢查都要再通過一次「AppContainer SID／capability」檢查：物件的 DACL 沒有授權該 AppContainer（或 ALL APPLICATION PACKAGES）就拒絕，與一般使用者權限無關。

## 2. 實作

| 項目 | 做法 | 位置 |
|---|---|---|
| 每次引擎呼叫獨立 AppContainer | `CreateAppContainerProfile` 以隨機名稱 `IMB-C.Engine.<PID>.<亂數>` 建立；名稱碰撞時絕不沿用，改用新名稱 | `low_integrity.rs` `Container` |
| 建立程序 | 沿用既有受限 Token（Administrators deny-only、Low IL、預設 DACL），再以 `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` 建立 AppContainer 程序；仍保留 `HANDLE_LIST`（只繼承三個標準串流）與 `JOB_LIST`（建立時原子納管） | `Sandbox::spawn` |
| 恢復前驗證 | 程序以暫停狀態建立；恢復前確認 Token 是 AppContainer、其 SID 等於本次建立的 SID、完整性為 Low、Administrators 未啟用。任一不符即終止，不恢復 | `Sandbox::spawn`、`app_container_sid` |
| 不留 profile 資料夾 | 恢復前呼叫 `DeleteAppContainerProfile`。Windows 會把 AppContainer 的 `TEMP`／`TMP`／`LOCALAPPDATA` 改寫到 profile 底下；刪除後這些位置不存在，引擎也無權在 `Packages` 下重建（實測） | 同上 |
| runtime 唯讀 | 自訂 capability `imbc-runtime`（SID 由 `DeriveCapabilitySidsFromName` 推導，單元測試核對）只取得 runtime 快取中清單檔案與目錄的讀取／執行 ACE。不授權給 ALL APPLICATION PACKAGES。**第二輪起不再修改 Portable 目錄 ACL**，改用每使用者、依版本與清單雜湊隔離的快取（見 v1.4-rc2-round2.md 第 1 節） | `runtime_cache` |
| 工作暫存 | 本次呼叫新建的暫存目錄 DACL 只授權擁有者、SYSTEM 與**本次** AppContainer SID，並保留 Low 標籤 | `Sandbox::grant_directory` |
| 需以路徑讀取的單一檔案 | 目標 ICC 快照等 IMB-C 產生的檔案，只對本次 SID 加入唯讀 ACE，工作目錄本身不開放 | `Sandbox::grant_file_read` |
| 禁止子程序 | `PROC_THREAD_ATTRIBUTE_CHILD_PROCESS_POLICY = RESTRICTED`。主控台程式初始化需建立 conhost.exe，與此政策衝突（實測 0xC0000142），因此改用 `DETACHED_PROCESS`；標準串流本來就是管線 | `Sandbox::spawn` |
| 引擎 Job | 作用中程序 1、`DIE_ON_UNHANDLED_EXCEPTION`、全部 UI 限制（他程序 USER 控制代碼、剪貼簿、全域 atom、桌面、系統參數、登出），保留記憶體上限與 `KILL_ON_JOB_CLOSE` | `ProcessGuard::engine` |
| 拒絕退回 | AppContainer 無法建立或驗證失敗時拒絕轉檔，不退回只有 Low IL 的模式 | `run_with_timeout` |
| 崩潰殘留 | 建立 profile 到恢復前崩潰會留下 profile。下次啟動只刪除建立者 PID 已結束的 `IMB-C.Engine.*`；建立者仍存在或無法判定一律保留 | `recover_stale_profiles` |

## 3. 磁碟用量（H-2）

| 層次 | 是否由 OS 或 IMB-C 在寫入前強制 | 說明 |
|---|---|---|
| 引擎可寫位置 | **OS 強制** | AppContainer 只能寫入本次暫存樹。LocalLow、Public、Windows\Temp、使用者資料夾、AppContainer profile、`Packages`、runtime 目錄、其他工作暫存、exFAT、SMB 都被拒絕（實測） |
| IMB-C 寫入的串流、副本與暫存峰值增量 | IMB-C 寫入前強制（固定上限） | 維持每個工作累計 32 GiB。曾嘗試降到該工作的磁碟預留量（`8 GiB + 48 B/px + 來源` 加輸出 `8 B/px + 64 MiB`）：16 MP 三種格式累計只用 1.25 GiB／8.90 GiB，但合法的 100 MP AVIF 轉檔超過約 13.3 GiB 而失敗。累計量包含已刪除的中介檔，不是正確的「實際佔用」指標，因此**撤回**，不為了通過測試放寬預留公式 |
| 暫存樹大小 | 輪詢強制（非 OS 配額） | 每約 40 ms 計算整棵暫存樹（原本只算 native cache 子目錄，HOME／profile 部分不在內）。改為以不跟隨連結的開啟查詢即時大小：目錄列舉對「仍開啟寫入中」的檔案大小會落後，實測舊做法讓 256 MiB 寫完才發現，新做法約 8 MiB 即停止 |
| 剩餘空間 | 輪詢強制 | 由每 250 ms 改為每次輪詢檢查暫存磁碟區至少 2 GiB |

**仍未解決：** 預留量（協調紀錄）與累計寫入上限（32 GiB）仍不相等；要讓兩者一致，需要以「實際存活的中介檔大小」而非累計量計算，本輪未完成。暫存樹大小與剩餘空間仍是輪詢後終止，不是檔案系統硬配額。被入侵的引擎可在一次輪詢間隔內（約 40 ms 加終止時間）以 `SetEndOfFile` 等方式短暫佔用剩餘空間，隨後被終止並清理。Windows 能強制的硬配額（NTFS 使用者配額、掛載固定大小 VHDX）都需要系統管理員權限，且 NTFS 配額以使用者為單位、無法區分工作；本輪不要求提升權限，因此**不宣稱 P1-1 已完全修復**。

## 4. 工作隔離（H-3）

- 不同工作使用不同 AppContainer SID；暫存目錄只授權各自的 SID。實測另一工作的暫存讀取、寫入、覆寫都被拒絕，也無法以修改權限開啟另一工作的程序。
- 未授權的一般使用者檔案連**讀取**都被拒絕（Low IL 時可讀）。
- 沒有網路 capability：本機迴路連線失敗、SMB 回報「網路存取被拒」。
- 仍可讀取授權 ALL APPLICATION PACKAGES 的系統位置（System32、Program Files 等），這些不是使用者資料。
- 仍未處理：核心漏洞造成的逃逸不在本機制範圍；同一使用者的**非 AppContainer** Low IL 程序（例如其他程式的低完整性程序）仍可寫入 IMB-C 的 Low 標籤暫存（與舊版相同，不屬於 IMB-C 工作之間）；iat 仍以 Medium IL 執行（選用、預設停用）。

## 5. FAT／exFAT 與遠端（H-1）

- RC2 先前做法是拒絕來源或輸出在無永久 ACL 磁碟區的轉檔。這只約束當次路徑，Low IL 引擎仍可寫入其他已掛載的 FAT／exFAT。
- 現在：AppContainer 無法以路徑開啟無 ACL 卸除式 exFAT 磁碟區上的檔案或列舉目錄（實測 G: exFAT，**只做唯讀開啟與列舉，沒有寫入**；同一檔案由 Medium IL 可開啟，證明拒絕來自隔離）。
- 來源不在本機 NTFS（FAT／exFAT、ReFS、其他檔案系統、遠端共用）時，IMB-C 從已開啟的控制代碼複製到本工作的受控暫存（本機 NTFS，引擎無權存取原位置），引擎只拿到副本的唯讀控制代碼。只讀原控制代碼、不以路徑重新開啟；複製期間長度改變即拒絕。
- 輸出由 IMB-C 以自己的控制代碼寫入與發布，引擎只寫管線，因此 FAT／exFAT／SMB 輸出目錄可以使用。
- 本機磁碟區能力無法判定時仍拒絕。不依磁碟代號推斷檔案系統。
- **未實機驗證：** FAT32、固定磁碟上的 FAT／exFAT、其他廠牌卸除式裝置、實體 ReFS 磁碟區、非本機 SMB／NAS。exFAT 的拒絕來自磁碟區裝置物件的安全描述元；本輪只在一個卸除式 exFAT 裝置上實測。

## 7. 給交叉審查的重點

1. `Sandbox::spawn` 的建立旗標（`DETACHED_PROCESS | EXTENDED_STARTUPINFO | UNICODE_ENVIRONMENT | SUSPENDED`）與恢復前驗證順序。開發時曾漏掉 `CREATE_SUSPENDED`，恢復前驗證因此拒絕啟動；請確認目前值 `0x0008040C`。
2. 預設 DACL 加入本次 AppContainer SID（缺少時子程序 DLL 初始化失敗 0xC0000142）。是否有其他物件因此被其他程序存取。
3. `ensure_runtime_access` 會永久修改 Portable 資料夾內 runtime 目錄的 ACL（加入自訂 capability 唯讀）。確認這對使用者可以接受，以及在唯讀媒體或權限不足時的錯誤訊息。
4. 累計寫入上限對齊預留量的嘗試與撤回理由（100 MP AVIF 實測失敗）；是否應改為追蹤存活中介檔大小。
5. `recover_stale_profiles` 只依 PID 判斷建立者是否存在；PID 重用時保守保留，不會誤刪。
